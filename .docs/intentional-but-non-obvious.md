# Intentional but Non-Obvious

This document outlines application behaviors that are intentional but non-obvious, and deemed too in-the-weeds for the top-level [`README.md`](../README.md).

- **Rollup and Profile order:** the active check takes the Profile's order in the list into account; the first Profile matched takes precedence. A number of things trigger off the active check, like when to skip switching to a Profile on Launcher activation. With audio-only Profiles vs full Profiles, a Launcher may do an unexpected "switch" even if the setup is fundamentally unchanged, just because of how activity is calculated between the two. For most use cases there is no real drawback to an additional switch, and there may be some benefit to letting the sort order decide, especially for users who mainly use the app for audio selection.
- **Profile deletion vs uninstall:** deleting a Profile **asks** whether to also delete its Launchers and Profile Shortcuts. By contrast, uninstalling the app *tries* to delete **all** known ones (along with config, logs, etc.), automatically and without a further prompt after the uninstall confirmation. In both cases, shortcuts that have been intentionally moved or renamed are considered owned by the user and are not touched.
- **Set audio device only offers devices that are accessible now.** This is by design, but it may not be obvious if you want to set up a TV soundbar before that device becomes accessible. Turning on the TV alone may not be enough to make the soundbar appear; you may have to actually use the TV as a display first (this might depend on the connection, e.g. HDMI vs optical; not tested). There is no issue picking the soundbar while the TV is in use as a display, and once created, these Profiles can be edited even when the TV is not active.
- **Hotkeys may be owned by other processes.** In my setup, F12 is the fourth default key, but it's typically hidden behind Steam's use of that key. This is OK: Display-Selector is meant to stay in the background and near-dormant, so it doesn't override other apps the user relies on. Users can re-assign hotkeys as they wish, so the control belongs to them. Display-Selector deconflicts its own hotkeys (one Profile per key, more or less at the desktop level), but not hotkeys that other applications use.
  - Saving a Profile (whose key is auto-assigned) and **Set hotkey…** both report a key they couldn't register. At startup, a key that can't be re-registered is only logged, so a key another app always owns doesn't nag on every sign-in.
- **Redaction differs between the clipboard actions.** **Submit bug report…** replaces the Windows user name with `%USER%` and copies only the most recent part of the log (about the last 6000 characters). **Copy diagnostics** and Profile Diagnostics' **Copy** copy the text as shown, unredacted, because they're meant for the user's own troubleshooting.
